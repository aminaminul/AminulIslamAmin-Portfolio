# Deployment

Target host: **MonsterASP.NET** (IIS + SQL Server). The same steps apply to any IIS host with the
ASP.NET Core Hosting Bundle, and the application has no GitHub dependency — GitHub is only one of
several upload methods.

> **Status:** this guide has been prepared against the host's published documentation. The
> application has **not** been deployed to a live MonsterASP.NET plan from this workspace, because
> that needs your account and credentials. Everything below that says "verify" must be confirmed on
> your plan before you rely on it.

## 1. Plan requirements

Check these on your plan before publishing:

| Requirement | Why | Where on MonsterASP.NET |
| --- | --- | --- |
| **.NET 10 (ASP.NET Core) runtime** | The project targets `net10.0`. MonsterASP.NET advertises .NET 10 hosting and configures new sites for ASP.NET Core ".NET 8 and newer", but confirm the runtime selector offers the version you publish. | **Websites → your site → Scripting → ASP.NET / .NET** |
| SQL Server 2019+ database | EF Core 10 + `Microsoft.Data.SqlClient` | **Databases → Add database** (SQL Server) |
| Persistent, writable application folder | Uploaded media and data-protection keys live in `App_Data` | Included in the plan's disk space; the host states scripts have full write permission on the site folder |
| Remote/console access *(optional)* | Applying migrations from your machine | **Databases → Users → Remote access** |
| Web Deploy or FTP/SFTP | Uploading the build | **Websites → Deploy** |

If your plan offers only an older runtime, publish for that runtime instead of forcing .NET 10:
change `<TargetFramework>` in the project (and the test project), restore, and re-run
`dotnet build -c Release` and `dotnet test` before deploying. Do not mix a .NET 10 build with a
.NET 8 application pool.

## 2. Build the deployment output

```bash
dotnet restore
dotnet build -c Release
dotnet test                                   # must be green before you publish
dotnet publish src/Portfolio.Web/Portfolio.Web.csproj -c Release -o ./publish
```

The output contains:

```
publish/
  Portfolio.Web.dll          application
  Portfolio.Web.deps.json
  Portfolio.Web.runtimeconfig.json
  web.config                 ASP.NET Core Module config (in-process by default)
  appsettings.json           non-secret configuration only
  wwwroot/                   css, js, images (no uploads)
  <package assemblies>       Markdig, MailKit, EF Core, SqlClient, Identity, …
  runtimes/                  native SQL client assets
```

`web.config` is generated by the SDK and uses `hostingModel="inprocess"` with
`processPath="dotnet"` — leave it as generated unless your host requires out-of-process hosting.

Never publish secrets, `App_Data`, `bin/obj` copies or source maps. `appsettings.Development.json`
is not copied into a Release publish (it is environment-scoped), and it must never be uploaded.

## 3. Create the site and database

1. **Create the website** — Control Panel → **New website** (or **Websites → Add website**), choose
   the plan, address and datacenter. Selecting "My own application" gives an empty site.
2. **Select the runtime** — **Websites → site → Scripting → ASP.NET / .NET**: choose modern .NET
   (ASP.NET Core). Saving recycles the application pool.
3. **Create the database** — **Databases → Add database → SQL Server**, same plan/base as the
   website so the connection is local and fast. The main user is created with the database.
4. **Copy the connection string** — **Databases → database → Users → Connection string**. Use the
   **local** string for the hosted site (the **remote** string only from your own machine, with
   remote access enabled for that user). Keep `TrustServerCertificate=True`.

Example (placeholders only):

```
Server=sqlXXX.monsterasp.net,1433;Database=dbXXXX;User Id=dbXXXX;Password=<password>;MultipleActiveResultSets=true;TrustServerCertificate=True;Encrypt=True
```

## 4. Configure the application

Use **Scripting → Environment variables** (restart the app after saving) so no secret ever sits in a
file in the repository:

| Variable | Value |
| --- | --- |
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `ConnectionStrings__DefaultConnection` | the local connection string from step 3 |
| `AdminSeed__Email` | your administrator email |
| `AdminSeed__Password` | a long unique password (remove this variable after the first sign-in) |
| `AdminSeed__DisplayName` | e.g. your name |
| `Site__PublicBaseUrl` | `https://your-domain.example` (used for sitemap/canonical URLs) |
| `Database__MigrateOnStartup` | `false` (keep it false; apply migrations deliberately in step 5) |
| `Email__Host`, `Email__Port`, `Email__UserName`, `Email__Password`, `Email__FromAddress`, `Email__ToAddress` | optional SMTP; leave empty to keep email disabled |
| `DataProtection__KeysPath` | `App_Data/keys` (default) — must be persistent |

A copy-paste template lives in [templates/appsettings.Production.example.json](templates/appsettings.Production.example.json).
Do not upload that file as `appsettings.Production.json` if it contains real values; environment
variables are preferred.

## 5. Apply the database schema

Two supported routes:

**A. From your machine against the remote database** (needs remote access enabled for the DB user):

```bash
export ConnectionStrings__DefaultConnection="<remote connection string>"
dotnet ef database update --project src/Portfolio.Web        # or: dotnet ef migrations script --idempotent
```

**B. Generate a script, run it through the host's SQL tooling:**

```bash
dotnet ef migrations script --idempotent --project src/Portfolio.Web --output migrate.sql
```

Review the script, back up the database, then execute it once. The idempotent form can be re-run
safely after future migrations.

Do **not** enable `Database:MigrateOnStartup` on a production database you have not backed up.

## 6. Media and persistence

Uploads are written to `App_Data/media/{images|documents}` and served through `/media/{id}`, so the
folder is never exposed as static files.

- MonsterASP.NET gives scripts write access to the site folder, and its git-deployment notes say
  untracked paths such as `uploads` and `App_Data` are left untouched by deployments — so an
  `App_Data` folder survives redeploys **there**.
- That is a hosting behaviour, not a guarantee on every provider. Verify after your first deploy:
  upload an image in **Media library**, confirm `/media/{id}` renders, redeploy, confirm it still
  renders.
- Include `App_Data` in your backups (database **and** files). Deleting it loses every upload and
  every data-protection key (which also signs out all administrators).
- If your plan has an ephemeral filesystem, point `Media:RootPath` at a persistent path, or replace
  `IMediaService` with an object-storage implementation — the interface is the only seam you need.

## 7. Upload

**Web Deploy (recommended, from Visual Studio or CLI)**

1. **Websites → site → Deploy**, enable WebDeploy, download the `.publishSettings` file.
2. Visual Studio: right-click the project → **Publish → Import profile** → select the file → Publish.
3. CLI equivalent:

```bash
dotnet publish src/Portfolio.Web -c Release -o ./publish
msdeploy.exe -verb:sync -source:contentPath="./publish" `
  -dest:contentPath="<site>,computerName=https://<server>:8172/msdeploy.axd,userName=<user>,password=<pass>,authType=Basic" `
  -enableRule:AppOffline
```

**FTP / SFTP**

1. **Websites → Deploy** gives server, port, user and password (prefer FTPS/SFTP).
2. Upload the **contents** of `./publish` into the site's document root (not into a subfolder).
3. Stop the app first (**Stop** button) or drop an `app_offline.htm` in the root, otherwise a running
   process may lock `Portfolio.Web.dll` and files will fail to overwrite. Remove it afterwards.

**ZIP deploy / git deploy** are also offered by the host; either is fine as long as `web.config`,
`wwwroot` and the assemblies land in the site root and `App_Data` is not wiped.

## 8. Post-deployment verification

Work through this list on the live origin:

| Check | Expected |
| --- | --- |
| `GET /` | 200, hero renders with your content, no CSS/JS 404 in devtools |
| `GET /Admin` while signed out | redirect to `/Admin/Account/Login` |
| Sign in with the seeded administrator | dashboard with real counts |
| **Profile → Save** | success toast, and the public header/hero/footer show the new values after a reload |
| Create a project as **Draft** | absent from `/projects`, `/projects/{slug}` returns 404 |
| Publish it | appears in `/projects`, detail page renders |
| Unpublish it | disappears again; 404 on the detail URL |
| Upload an image in **Media library** | preview renders from `/media/{id}` |
| Upload the CV and open `/cv` | PDF downloads |
| Submit the contact form | message appears in **Admin → Messages**; wording reflects whether email is configured |
| `/sitemap.xml`, `/robots.txt` | 200, no `/Admin` entries, no drafts |
| Response headers | `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy` present |
| `https://` only | HTTP redirects to HTTPS; cookies marked `Secure` |

Also confirm the log shows `Provisioned administrator …` exactly once, and that no `Failed to
determine the https port` warning appears in Production (it is a development-only symptom).

## 9. Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| **HTTP 500.30 / 500.31 – In-Process start failure** | The app pool .NET version does not match the published TFM, or `web.config` refers to a missing `*.dll`. Set **Scripting → .NET** to the matching version, republish, check `logs/stdout`. |
| **HTTP 500.19 – config error** | Malformed or hand-edited `web.config`, or the ASP.NET Core Module is missing. Restore the generated file; ensure the Hosting Bundle is installed on the server (host responsibility). |
| **HTTP 502.5 – process failure** | Runtime not installed for the app pool, or a startup exception. Enable stdout logging in `web.config` (`stdoutLogEnabled="true"`) and read `logs/stdout_*.log`. |
| **Empty white page, 200 status** | Static assets missing — `wwwroot` not uploaded, or the app published but files uploaded into a subdirectory. |
| **No CSS/JS, 404 under `/css/...`** | Same as above; also check the site root path in the control panel. |
| **`ConnectionStrings:DefaultConnection is required`** | Environment variable not set, or named `ConnectionStrings:DefaultConnection` (colon) instead of `ConnectionStrings__DefaultConnection` (double underscore). |
| **`The SQL Server database is not reachable`** | Wrong server/user/password, database not on the same plan, or `TrustServerCertificate` removed against a self-signed server certificate. |
| **Login succeeds then immediately signs out / antiforgery errors** | Data-protection keys are not persistent. Ensure `App_Data/keys` exists and survives redeploys, or set `DataProtection__KeysPath` to a persistent path. |
| **`Invalid object name 'Projects'`** | Migrations were never applied. Run step 5 and restart. |
| **Uploads fail with "file is too large"** | The plan's request limit is lower than 8 MB/20 MB. Raise `Media:MaxImageBytes`/`MaxDocumentBytes` only if the host allows it, or reduce the limit. |
| **Uploads disappear after redeploy** | `App_Data` was wiped. Use persistent storage (see section 6). |
| **Broken image after replacing a file** | The old media id no longer exists; re-select the image in the form so the content row points at the new media record. |
| **Bangla text shows boxes** | The page cannot reach Google Fonts; self-host `Noto Sans Bengali` and adjust the CSP `font-src`. |
| **Administrator cannot be created** | `AdminSeed__Password` does not meet the 12-character policy, or the email already exists without the role. Read the log line, fix, restart. |

### Expected log lines that are not errors

| Line | Meaning |
| --- | --- |
| `warn: No administrator seed credentials supplied` | Normal once `AdminSeed` has been removed (or before it is set). The site serves fine; sign-in only works for existing accounts. |
| `warn: DataProtection … No XML encryptor configured` | The key ring on disk is protected by file permissions only. Acceptable on a single-tenant host; use `ProtectKeysWith*` if you need keys encrypted at rest. |
| `warn: Failed to determine the https port for redirect` | The site was started on plain HTTP without an HTTPS binding. Under IIS with an HTTPS binding this disappears. |

## 10. Portability to other hosts

Nothing in the application depends on MonsterASP.NET or GitHub:

- Any IIS host with the ASP.NET Core Hosting Bundle works with the same publish output.
- Linux/Kestrel hosts work by publishing `-r linux-x64 --self-contained false` (or framework
  dependent) and running `dotnet Portfolio.Web.dll` behind a reverse proxy; keep
  `DataProtection__KeysPath` and `Media__RootPath` on persistent volumes.
- Azure App Service / container hosts work the same way; only the environment-variable and storage
  configuration changes.
- The only host-specific inputs are the connection string, the two paths above and the public base
  URL.
